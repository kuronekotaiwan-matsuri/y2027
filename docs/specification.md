# サイト仕様書: 黒猫台湾まつり2027

## 0. この文書について

- 本書は、`docs/concept/concept.md` で定めたコンセプトを、実際に作るWebサイトの仕様に落としたもの。
- コンセプトが「何を目指すか」、本書が「何をどう作るか」を担当する。
- サイトは祭りと一緒に育てる方針のため、本書も完成版ではない。ページや機能を追加するたびに更新する。
- 判断に迷ったときはコンセプトに戻る。とくに次の3点を優先する。
  - 完成していないことを隠さない
  - 記録を書くだけでサイトが育つ
  - いろいろな人が作っていることが見える

## 1. 概要

### 1.1 サイトの目的

黒猫台湾まつり2027の公式サイト。

主コンテンツは、過去のサイトと同じく**祭りの案内**（開催情報、出店、プログラム、タイムテーブル、会場、アクセスなど）。
来場を考える人が知りたいことに答えるのが第一の役割。

これに加えて、2027年はサブコンテンツとして**「黒猫台湾まつりができるまで」**を持つ。
2026年10月から開催までの過程を「記録」として蓄積し、物語として読めるようにする。
祭りの案内がまだ決まっていない時期は、この記録が「いまどこまで決まっているか」を伝える役目も担う。

つまり、

- 案内: 決まったことを載せる場所。内容は開催が近づくにつれて埋まる
- できるまで: 決まっていく過程を載せる場所。公開初日から動いている

の2つを持ち、できるまでが案内を育てていく。

サイトの構造（ナビの順序、URLの階層）では案内を主、できるまでをサブとして固定する。
一方、トップページで前面に出す「主役」は時期によって切り替える（2.4参照、コンセプト11項）。
準備期間はできるまで、開催が近づいたら案内、開催後は記録が主役になる。

### 1.2 ターゲットユーザー

| 誰 | 来る経路 | サイトに求めること |
|---|---|---|
| 来場を検討している人 | Google検索、口コミ、店頭QR | いつ・どこで・何があるか。出店とプログラム。今どこまで決まっているか |
| 途中から知った人 | Instagram、出店者や出演者のSNS | 祭りの概要と、最初からの経緯 |
| 関わり始めた人（若者チーム、出店者、出演者、ボランティア、地域店舗） | 運営からの共有、自分の投稿 | 自分の記録が自分の名前で載っていること。人に見せられるURL（書き手ページ） |
| 関わるか迷っている人 | Instagram、知人の紹介 | どんな人がどう関わっているか。入り口がどこか |
| 地域メディア・台湾関係者 | 検索、紹介 | 経緯と背景がまとまった一次情報 |

### 1.3 サイトのゴール

- 開催情報・出店・プログラムなど、来場者が必要とする案内を、決まり次第すぐ載せられること
- 記録を継続的に追加できること（更新が負担にならないこと）
- 途中から見た人が、最初から今までを追えること
- 「関わる人」が増えていく様子が、サイト上で見えること
- 各所からの流入を受け止める「母艦」として機能すること

### 1.4 非目標（やらないこと）

- CMSや管理画面などの、Markdown以外の入力経路（現段階では不要）
- サイト上のコメント機能、フォーム、ログイン（反応はInstagramとメールで受ける）
- Webサイト単体での集客施策の作り込み（流入はSNSなど外部に任せる）
- 公開時点での完成度の追求（最小構成で公開し、育てる）

## 2. コンテンツ構成

### 2.1 主コンテンツ: 祭りの案内

過去のサイト（2025・2026）と同系統の内容。決まったことを載せる。

| 内容 | 概要 | 状態（2026年9月時点） |
|---|---|---|
| 開催情報 | 日程、時間、会場、入場料、主催・後援 | 未定 |
| 出店情報 | 出店者一覧（カテゴリ、出店日、紹介、SNS） | 未定 |
| プログラム | 出演者、ワークショップ、ステージ、トークなど | 未定 |
| タイムテーブル | 日ごとの時間割 | 未定 |
| 会場マップ | 会場構成と各ブースの位置 | 未定 |
| アクセス | 最寄駅、行き方、駐車場・駐輪場の案内 | 未定 |
| ボランティア募集 | 募集内容と申込先 | 未定 |
| お問合せ・FAQ | よくある質問と連絡先 | 一部（連絡先は確定） |
| プレスリリース | 報道向け | 未定 |

- データは 2026年と同様、TypeScript または JSON の定数として `src/data/` に置く（項目の詳細は各ページを追加するときに決める）
- 未定の内容は「準備中」として扱う（5.2参照）。ページがない状態ではなく、「まだ決まっていない」と書かれたページがある状態にする
- 決まったら、データを入れて本番の内容に切り替える。切り替えたことは記録としても投稿する

### 2.2 サブコンテンツ: できるまで

「記録」と「書き手」からなる。3章で詳述する。読者に見せる第一の識別子は「誰が書いたか」（顔と名前）であり、立場はそれに添える情報にする（3.8参照）。

- サイト内では `/making/` 配下にまとめ、主コンテンツと階層で区別する
- ナビとURL階層では主コンテンツより後ろに置く。トップでの位置は時期による（2.4参照）
- 準備期間（`phase: making`）は、トップの主役はここになる

### 2.3 主とサブのつながり

- 記録には `topics`（出店、プログラム、会場など）を付けられる。主コンテンツの「準備中」ページは、自分に関係する記録をここから拾って「いまの状況」として表示する
- 主コンテンツが本番に切り替わった後も、そのページの末尾に関連する記録を「ここまでの経緯」として残す
- 主コンテンツの追加・公開は、それ自体を記録にする（例: 「出店情報を公開しました」）

### 2.4 時期による主役の切り替え

コンセプト11項のとおり、トップページの主役は固定しない。設定ファイル（`src/config/site.ts`）の `phase` で切り替える。

| phase | 時期 | トップの主役 | サイトの役割（コンセプト11項） |
|---|---|---|---|
| `making` | 公開から、開催情報が固まるまで | できるまで | 参加したくなるサイト |
| `event` | 開催情報が固まってから開催まで | 祭りの案内 | 行きたくなる・使いやすいサイト |
| `archive` | 開催後 | 開催の記録と振り返り | また関わりたくなるサイト |

- 切り替えは `site.ts` の1項目を変えるだけ。ページやコンポーネントの作り直しはしない
- phase で変わるのは、トップのセクションの並び順とヒーローの内容（5.1参照）。各ページの中身は変わらない
- ナビの順序とURL階層は phase によらず固定する（探しやすさを優先）
- `event` に切り替える時期は実行委員会が判断する（目安: 出店情報を本番に切り替えるとき）
- `archive` では、当日の様子と振り返りを記録として加え、準備から開催までをひとつの記録として残す。次回の資産にする

## 3. できるまでのデータモデル

### 3.1 記録（Record）

できるまでの最小単位。出来事1つ。書き手が日常的に追加するもの。

- 必ず1人の書き手（3.2参照）が書く。
- 「決まったこと」だけでなく、「迷っていること」「試したこと」「うまくいかなかったこと」「ボツ案」も記録にする。
- 1つの記録は短くてよい。写真1枚と数行の文章で成立する。
- Instagram投稿があればURLを添える（3.4参照）。
- 主コンテンツに関係する記録には `topics` を付ける（3.3参照）。
- 記録をまとめる「物語」のような上位の単位は持たない（2026年9月に廃止。分類のラベルより「誰が書いたか」で読む方が分かりやすいため）。ある人の取り組みを通しで読むには書き手ページ（5.5参照）を使う。

記録が持つ情報:

| 項目 | 内容 |
|---|---|
| slug | ファイル名から決まる（`YYYY-MM-DD-<短い英語名>`） |
| title | 見出し。「今年も動き始めました」のような、出来事がわかる文 |
| date | 出来事の日付（公開日ではなく、起きた日） |
| author | 書き手のID（3.2参照） |
| summary | タイムラインに表示する一行の要約 |
| tags | 状態や種類を示すタグ（3.3参照。任意） |
| topics | 関係する主コンテンツ（3.3参照。任意） |
| thumbnail | タイムラインとOGPに使う代表画像（任意） |
| instagram | 関連するInstagram投稿のURL（任意・複数可） |
| draft | `true` のとき公開しない（下書き） |
| 本文 | Markdown。写真、手書きメモの画像、スケッチなどを自由に入れる |

### 3.2 書き手（Person）と立場（role）

いろいろな人の声が存在するサイトにするため、記録には必ず「誰が書いたか」を付ける。
読者に見せる第一の識別子は**人（顔と名前）**であり、立場は名前に添える情報にする。
参考にしたのは、多数の書き手が並んでも混乱しないサイトの共通点（note、Burning Man Journal、GitHub の議論欄、dev.to）: 一覧では顔と名前、役割は名前の横に小さく、開いた先の末尾に本人の自己紹介。
見せ方は `docs/design-lab/v4/` で比較して決めた（カードは案01、記録ページは案02）。

書き手は `content/people/<id>.md` に1人1ファイルで登録し、記録はIDで参照する。組織も1つの書き手として登録できる。

書き手が持つ情報:

| 項目 | 内容 |
|---|---|
| id | ファイル名（英小文字・数字・ハイフン）。記録の `author` から参照する |
| name | 公開してよい名前（ニックネーム可）。組織なら組織名 |
| shortName | 顔の下や「〇〇の記録」の見出しで使う短い名前。任意。組織名が長いとき（例: 「黒猫台湾まつり実行委員会」→「実行委員会」）。署名、書いた人カード、作っている人たち、書き手ページの h1 は `name` のまま |
| role | 立場（下表） |
| kind | `person`（既定） / `group`（組織。署名に立場を添えず、顔は黒猫のマーク） |
| avatar | 顔写真やイラスト（任意。`/images/people/<id>.jpg`）。無いときは名前の1文字目を丸の中に出す |
| bio | 一言の自己紹介（1〜2文。例: 「実行委員。2023年の第1回から関わっています。」） |
| instagram | 本人のアカウントURL（任意） |
| order | 「作っている人たち」と「顔で絞る」での並び順（任意。既定はID順） |
| draft | `true` のとき公開しない。その書き手の記録も公開しない |
| 本文 | 長めの自己紹介（任意。書き手ページに表示） |

立場（`role`）:

| role | 表示 |
|---|---|
| `committee` | 実行委員 |
| `youth` | 若者チーム |
| `shop` | 出店者 |
| `performer` | 出演者 |
| `volunteer` | ボランティア |
| `local` | 地域の人・お店 |
| `taiwan` | 台湾関係者 |
| `other` | その他 |

- 署名（byline）は「顔 + 名前 + 立場」を1組で出す。立場だけを単独のバッジとして出さない。
- 一覧（カード）では立場を小さな枠のラベルで、記録ページでは「イケダ（出店者）」のように文字で添える。
- 記録ページの末尾には「書いた人」カード（顔、名前、立場、自己紹介、その人の記録一覧へのリンク）を置く。
- 書き手は1人ずつ書き手ページ（5.5参照）を持つ。
- 公式の発表（出店者募集、日程確定など）は組織の書き手「黒猫台湾まつり実行委員会」（`committee`、`kind: group`）名義で書く。実行委員が中の人として書くときは個人名（例: 池田）で書く。
- 立場の一覧は将来増やせるようにする（設定ファイルで管理）。

### 3.3 タグ（状態）とトピック（主コンテンツとの紐付け）

**タグ**は「まだ決まっていない」こと自体をコンテンツにするための、記録の状態。自由記述だが、次の語彙を推奨する。

| タグ | 意味 |
|---|---|
| 検討中 | 案を出している。まだ決まっていない |
| 試作中 | 作ってみている途中 |
| 決定 | 決まった |
| ボツ | やめた。うまくいかなかった |
| 募集中 | 人や店や意見を集めている |
| 開催情報 | 日時・会場など、来場者向けの確定情報 |

タグは表示のみに使う。フィルタ機能は初期公開では作らない（記録が増えてから検討）。

**トピック**は、記録がどの主コンテンツに関係するかを示す。主コンテンツの準備中ページが関連記録を拾うために使う。

| topic | 対応する主コンテンツ |
|---|---|
| `event` | 開催情報（日程・会場） |
| `shops` | 出店情報 |
| `programs` | プログラム（出演・ワークショップ・ステージ） |
| `venue` | 会場マップ |
| `access` | アクセス |
| `volunteer` | ボランティア募集 |
| `poster` | ポスター・チラシなど広報物 |

複数指定可。付けなくてもよい。語彙は設定ファイルで管理し、主コンテンツが増えたら足す。

### 3.4 Instagramの扱い

- 役割分担: Instagramは生中継、Webサイトはドキュメンタリー／アーカイブ。
- 記録の `instagram` 項目に投稿URLを書く。サイト上では公式埋め込みを使わず、リンクカード（Instagramアイコン + 「Instagramで見る」）として表示する。
- 理由:
  - 静的サイトで確実に動き、外部スクリプトに依存しない
  - 投稿の削除や仕様変更でページが崩れない
  - 記録側に写真と文章を書くため、Web単体でも読める
- 将来公式埋め込みに切り替える場合も、URLは同じなので記録の書き直しは不要。
- 公式アカウントへのリンクはヘッダーとフッターに常設する。

### 3.5 ディレクトリ構成とファイル命名

記録は1つのフォルダに並べ、書き手は1人1ファイル。
記録の追加はファイルを1つ、書き手の追加もファイルを1つ足すだけで済む。

```text
content/
├─ README.md                        # このフォルダの書き方（短い版。詳細は docs/writing-guide.md）
├─ people/                          # 書き手（1人1ファイル）
│  ├─ committee.md                  # 黒猫台湾まつり実行委員会（組織。公式発表用）
│  ├─ ikeda.md                      # 池田（実行委員）
│  ├─ ikeda-shop.md                 # イケダ（出店者）。同じ人の別の立場
│  └─ ...
└─ records/                         # 記録（1出来事 = 1ファイル）
   ├─ 2026-10-05-kickoff.md
   ├─ 2026-10-20-what-to-sell.md
   ├─ 2026-11-12-brainstorm.md
   └─ ...

public/
└─ images/
   ├─ people/                       # 顔写真（任意）
   │  └─ ikeda.jpg
   └─ records/
      └─ 2026-10-05-kickoff/        # 記録slugと同名のフォルダに画像を置く
         ├─ 01.jpg
         └─ memo.jpg
```

命名規則:

- 書き手ID: 英小文字・数字・ハイフン。例 `ikeda`, `ikeda-shop`, `committee`
- 記録ファイル名: `YYYY-MM-DD-<短い英語名>.md`。日付は出来事の日
- 記録slug = ファイル名から `.md` を除いたもの。サイト全体で一意
- 画像: `public/images/records/<記録slug>/` に置き、本文からは `/images/records/<記録slug>/01.jpg` と書く（`basePath` はビルド時に自動付与）

### 3.6 front-matterスキーマ

書き手（`people/<id>.md`）:

```yaml
---
name: 池田
shortName: 池田         # 任意。顔の下や「〇〇の記録」の見出しで使う短い名前。組織名が長いときに書く（例: 実行委員会）
role: committee         # 3.2 の立場から1つ
kind: person            # person | group。任意。既定 person
avatar: /images/people/ikeda.jpg   # 任意
bio: 実行委員。2023年の第1回から関わっています。   # 任意だが推奨
instagram: https://www.instagram.com/xxxx/         # 任意
order: 2                # 任意
draft: false            # 任意。既定 false
---
（長めの自己紹介。任意）
```

記録（`records/YYYY-MM-DD-<name>.md`）:

```yaml
---
title: 今年も動き始めました
date: 2026-10-05
author: ikeda                                                  # 書き手のID
summary: 2027年に向けて、まず4人で集まりました。まだ何も決まっていません。
tags: [検討中]
topics: [event]                                                # 任意
thumbnail: /images/records/2026-10-05-kickoff/01.jpg           # 任意
instagram:                                                     # 任意
  - https://www.instagram.com/p/xxxxxxxx/
draft: false                                                   # 任意。既定 false
---
（本文。Markdown）
```

必須項目: 書き手は `name`, `role`。記録は `title`, `date`, `author`, `summary`。
必須項目の欠落、存在しない `role` や `topics`、`content/people/` に無い `author` は、ビルドを失敗させて書き手に知らせる（9.4参照）。

### 3.7 一人が二つの立場で書くとき

実行委員が個人として店を出すなど、一人が二つの立場を持つときは、**別の書き手として登録する**（例: 「池田（実行委員）」と「イケダ（出店者）」）。

- 最初の記録で「実行委員の池田と同じ人です」と本人が明かす。書き手の自己紹介にも書く。
- 公式でない活動であることを示す注記や色分けはしない。署名の立場（出店者）がそれを表す。
- 二つの書き手はそれぞれ書き手ページを持つ。互いの自己紹介から行き来できる。

### 3.8 読者に見せる言葉

データ上の分類名（立場、トピック、書き手のID）は、読者向けの画面にそのまま出さない。小学生が初見で読めることを基準にする。

| データ上の概念 | 画面での見せ方 |
|---|---|
| 書き手 | 顔と名前。立場は名前の横に小さく（例: 池田 実行委員、イケダ（出店者）） |
| 組織の書き手 | 名前だけ（黒猫台湾まつり実行委員会）。顔は黒猫のマーク |
| タグ（状態） | 判子（検討中・ボツ・決定など）。読者向けの言葉なのでそのまま出す |
| トピック | 「関連する案内: 出店情報」のようにリンクの文で |

## 5. 各ページの詳細

### 5.1 トップ（`/`）

役割: 時期に応じた主役を前面に出し、決まっていないことは決まっていないと伝える。

セクションは共通で、`phase`（2.4参照）によって並び順とヒーローの内容だけが変わる。

セクション:

- **ヒーロー**
  - サイト名「黒猫台湾まつり2027」とキャッチコピー（案: 「黒猫台湾まつりは、5月に始まるのではない。」実装時に確認）
  - `making`: 「いま」の表示（最新の記録の月とタイトル。例「2026.10 今年も動き始めました」）を主に置き、開催予定「2027年5月 開催予定（日程・会場未定）」を添える。CTA「できるまでを見る」
  - `event`: 開催情報（日程・時間・会場・入場料）を主に置く。CTA「出店情報を見る」「プログラムを見る」。できるまでへの導線は小さく残す
  - `archive`: 「2027年5月◯日 開催しました」と当日の写真。CTA「できるまでを最初から読む」
- **開催情報と案内メニュー**
  - 開催情報の項目（日程、会場、時間、入場料）。未定の項目は「未定」と表示
  - 出店情報、プログラム、（追加後は）タイムテーブル、会場マップ、アクセスへのカード。各カードに状態「準備中」または「公開中」。準備中でもクリックでき、準備中ページへ飛ぶ
  - 存在しないページはカードにしない
  - `archive` では「2027年の記録」として同じ内容をアーカイブ表示する
- **できるまで**
  - 見出し「黒猫台湾まつりができるまで」と短いリード
  - 最新の記録3件。署名（顔・名前・立場）、日付、タイトル、要約、状態タグ、サムネイル
  - 「書いている人たち」: 書き手の顔と名前の並び（`order` 順）。押すと書き手ページへ
  - 「すべて見る」で `/making/` へ
  - `archive` では最新3件の代わりに「開催の記録」と「振り返り」を表示
- **黒猫台湾まつりとは（要約）**
  - 3〜4行の説明と `/about/` への導線
- **関わる・見守る**
  - Instagramへの導線（「日々の様子はInstagramで」）
  - メールアドレス
  - 「意見を言う・関わる」の入り口として、当面はInstagramのDMとメールを案内

phase ごとの並び（上から）:

| phase | 並び |
|---|---|
| `making` | ヒーロー → できるまで → 開催情報と案内メニュー → まつりとは → 関わる |
| `event` | ヒーロー → 開催情報と案内メニュー → できるまで → まつりとは → 関わる |
| `archive` | ヒーロー → できるまで（開催の記録・振り返り） → 開催情報と案内メニュー（アーカイブ表示） → まつりとは → 関わる |

### 5.2 主コンテンツの準備中ページ（`/shops/`, `/programs/` など）

役割: 「まだ決まっていない」ことを、来場者向けの言葉で伝える。あわせて、決まるまでの過程を見せる。

構成:

1. **見出し**（例: 「出店情報」）と状態バッジ「準備中」
2. **いまの状況**
   - 設定ファイル（`src/config/site.ts`）に書いた短い文。例: 「出店者はまだ決まっていません。2027年1月ごろに募集を始める予定です。」
   - 更新日
3. **関連する記録**
   - このページの `topic` を持つ記録を、新しい順に表示（タイムラインと同じ部品）
   - 記録がなければ「まだ記録はありません」
4. **決まったらここに載ります**
   - 本番で載せる予定の項目を箇条書き（例: 出店者名、カテゴリ、出店日、紹介文、SNS）。参考として2026年のページへのリンク
5. **Instagramと問い合わせ先**

本番に切り替えるとき:

- 状態バッジを外し、データから一覧を生成する（詳細は切り替え時に本書へ追記）
- 「関連する記録」はページ末尾に「ここまでの経緯」として残す
- 「〇〇を公開しました」の記録を投稿する

### 5.3 できるまで（`/making/`）

役割: サブコンテンツの入口。2026年10月から2027年5月までを、1本の時系列で読む。

構成:

1. **見出し**「黒猫台湾まつりができるまで」と短いリード
2. **顔で絞る**
   - 「すべて」と各書き手の顔（名前つき）。押すとその人の記録だけに絞る（クライアント側。状態はURLのクエリ `?by=<id>` に持ち、共有できるようにする）
   - 既定は「すべて」。並びは書き手の `order`
   - 記録が0件の書き手も出す（登録した時点で「関わっている」ことが見える）
3. **タイムライン本体**
   - 縦一列。上が古く、下が新しい（最初から追える読み方を優先）
   - 月の区切りを「2026.10」の形で表示
   - 各記録: 署名（顔・名前・立場の小さな枠）、日付、タイトル、要約、状態タグ、サムネイル（あれば）。カード全体で記録ページへ
4. **ゴールマーカー**
   - 最下部に「2027.05 黒猫台湾まつり2027 開催（予定）」を固定表示。日程確定後は日付を表示
   - 設定（`site.event.goal`）では日付・名前・状態の3つに分けて持ち、折り返しが語の途中で起きないようにする
   - 開催後は、開催の記録がこの位置に置き換わる
5. **最新へのジャンプ**
   - ページ上部に「最新の記録へ」リンク（記録が増えたときのため）。顔で絞った結果が0件のときは出さない

表示件数: 初期は全件表示。1画面に収まらなくなったら月単位の折りたたみを検討する。

### 5.4 記録（`/making/records/<記録slug>/`）

役割: 出来事1件を読む。SNSや口コミで共有される単位。開いた人が「どこに来たか」「誰が書いたか」をすぐ分かるようにする。

構成:

1. **パンくず**: 「できるまで」へのリンク（このページがタイムラインの1件であることを示す）
2. **ヘッダー**
   - タイトル
   - 署名（顔と「イケダ（出店者）」の形の文字）、日付、状態タグ
   - `topics` があれば、「関連する案内: 出店情報」のように対応する主コンテンツへのリンク
3. **本文**（Markdownを描画）
   - 画像は幅いっぱいに、キャプション付きで表示できる
   - 手書きメモやスケッチの写真も本文画像として扱う
4. **Instagramリンクカード**（`instagram` があるとき）
   - 投稿ごとに1枚。アイコン、「Instagramで見る」、新しいタブで開く
5. **書いた人**: 顔、名前、立場、自己紹介、「〇〇さんの記録をすべて見る」（書き手ページへ）
6. **前後の記録**: 全体タイムラインでの前へ・次へ（1組だけ）
7. **できるまでへ戻る**リンク

OGP: `thumbnail` があればそれを、なければサイト共通画像を使う。タイトルは「記録タイトル | 黒猫台湾まつり2027」。

### 5.5 書き手（`/making/people/<id>/`）

役割: 1人の書き手の記録をまとめて読む（note のクリエイターページに相当）。本人が「私はこれをやっています」と人に見せるページ。「作っている人たち」（5.6）、「書いている人たち」（5.1）、記録ページの「書いた人」から辿る。

構成:

1. **パンくず**: 「できるまで」へのリンク
2. **書き手ヘッダー**: 顔、名前、立場、自己紹介、（あれば）Instagram へのリンク
3. **自己紹介の本文**（`content/people/<id>.md` の本文。あれば）
4. **〇〇さんの記録**: タイムライン形式（5.3と同じ部品。上が古い）。記録が無ければ「まだ記録はありません」
5. **できるまでへ戻る**リンク

`draft: true` でない書き手は、記録が0件でもページを生成する。
OGP: `avatar` があればそれを、なければサイト共通画像。タイトルは「名前 | 黒猫台湾まつり2027」。

### 5.6 黒猫台湾まつりとは（`/about/`）

役割: 途中から知った人に、そもそも何の祭りかを説明する。

構成:

1. **黒猫台湾まつりとは**: 台湾文化、地域（大山街道・二子新地）、人の交流という3つの柱を短く
2. **これまでの歩み**: 第1回から第4回（2026年）までを年表で。各年の過去サイトへのリンク
3. **2027年の挑戦**: コンセプトから「過程を公開する」「若者への権限移譲」「関わる人を増やす」を要約
4. **作っている人たち**: 登録された書き手（`content/people/`）を顔・名前・立場・自己紹介で一覧し、書き手ページへリンクする。名前は本人が公開してよい範囲で
5. **関わり方**: Instagram、メール、（募集を始めたら）ボランティア募集への導線

### 5.7 あとから追加するページの扱い

- 追加時に本書の4.3を5章へ昇格させ、詳細を書く。
- 追加したページへの導線をヘッダーとトップの案内メニューに増やし、「〇〇ページを公開しました」を記録として投稿する。

## 7. デザイン

### 7.1 確定したデザイン「机の上の商店街」

design-lab（`docs/design-lab/`）で2ラウンドの比較を行い、第2ラウンドの案02 を採用した。
確定値は `docs/design-system.md` にある。本書では方向性だけを記す。

- 世界観: 祭りを作っている人の机の上。商店街の色の紙に、ペン字でメモを書き、写真をテープで貼り、決まったことに判子を押している
- 書体: 見出しはペン字（Klee One）、本文は丸ゴシック（Zen Maru Gothic）。2026年の丸ゴシックは本文で引き継ぐ
- 色: クリーム `#FBF3E4` の紙に、赤 `#B7332A`（公式・判子）、紺 `#1F3A5F`（個人・リンク）、金 `#D9A62E`（テープ・罫線）、付箋の黄 `#FFF3B0`
- 形: 角丸は小さく（4〜6px）、ボタンとタグはピル型。カードはわずかに傾き、テープで留める
- モバイルファースト

### 7.2 主コンテンツとサブコンテンツの見た目の使い分け

- 主コンテンツ（出店・プログラムなど）は、同じトークンで作るが、傾きやテープなどの「途中の空気」は控えめにする。来場者が情報を探すページなので、整列と読みやすさを優先する
- 準備中ページは、状態バッジ「準備中」と関連記録で「途中」であることを示す。それ以外は主コンテンツと同じ整った見た目にする
- サブコンテンツ（できるまで）は、design-lab の見本のとおり、傾き・テープ・付箋・判子を使う
- 同じ部品（タイムライン、記録カード）を主ページに置くときも見た目は変えない。ページ全体の整い方で区別する

### 7.3 作っている途中の空気の出し方

- 手書き感は書体・傾き・テープ・付箋で出す。写真や画像の加工では出さない
- 写真、手書きメモ、スケッチ、試作品、打ち合わせ風景、ボツ案を、整った画像と同列に扱う。スマホ写真のままポラロイド風の台紙に入れる
- 「検討中」「ボツ」などの状態は判子風のタグで示す。ボツは打ち消し線
- 書き手の顔と名前を毎回出して、いろいろな人が並んで書いていることを見せる。分類のための色分けはしない
- サイトの余白や部品は整えつつ、中身は途中でよい、という切り分け

### 7.4 レイアウト

- タイムラインはモバイルで縦1列、デスクトップでも縦1列を基本とする（左右交互配置はしない。読む順が乱れるため）
- 記録本文の最大幅は読みやすさ優先で 700px 程度
- 画像は幅いっぱい、キャプション付き
- 主コンテンツの一覧（出店・プログラム）は 2026年と同様のカードグリッド（3列、モバイル1列）

## 8. 更新運用

コンセプト15項「記録を書く → 自動的にタイムラインに追加される」を実現する手順。

### 8.1 記録を追加する

1. 画像があれば `public/images/records/<記録slug>/` に置く
2. `content/records/YYYY-MM-DD-<name>.md` を作り、front-matterと本文を書く。`author` には自分の書き手IDを書く（初めての人は先に 8.2 で登録する）
3. 主コンテンツに関係する内容なら `topics` を付ける
4. `main` にpushする（またはPull Requestをマージする）
5. GitHub Actionsが自動でビルド・公開する。数分で反映

`npm run new:record <name>` で、日付入りファイル名とfront-matterの雛形を生成できるようにする（任意だが推奨）。

### 8.2 書き手を追加する

1. `content/people/<id>.md` を作り、名前・立場・自己紹介を書く
2. 顔写真があれば `public/images/people/<id>.jpg` に置き、`avatar` に書く
3. pushすると、「作っている人たち」「書いている人たち」「顔で絞る」と書き手ページが自動で増える

一人が二つの立場で書くときは、書き手を2つ登録する（3.7参照）。

### 8.3 主コンテンツを更新する

- 開催情報や準備中ページの「いまの状況」の文は、設定ファイル（`src/config/site.ts`）を書き換える
- トップの主役を切り替えるときは、同じ設定ファイルの `phase` を変える（2.4参照）
- 出店・プログラムなどのデータは `src/data/` の定数を編集する
- 更新したら、あわせて記録を投稿する（例: 「日程が決まりました」「出店情報を公開しました」）。これがサブコンテンツと主コンテンツをつなぐ

### 8.4 書き方の目安

- 1記録は短くてよい。写真1枚と3行で成立する
- 決まっていないことは「決まっていない」と書く。タグ「検討中」を付ける
- 失敗やボツも記録にする。タグ「ボツ」を付ける
- 日付は出来事の日。あとからまとめて書いてもよい
- Instagramに投稿した内容は、URLを添えて短く記録に残す
- 出店・会場など主コンテンツに関わる話には `topics` を付ける。準備中ページに自動で載る
- 画像のキャプションは `![代替文](/images/... "キャプション")` の title で書く。本文に生の HTML は書けない（無視される）
- `instagram` は `https://` で始まる URL のみ。`tags` と `instagram` は1つなら文字列、複数なら配列でよい
- 手順の詳細と front-matter の雛形は `docs/writing-guide.md`

### 8.5 公開の流れ

- ブランチ運用: `main` へのpushで本番公開。作業は任意のブランチで行い、`main` にマージする
- 下書き: `draft: true` の記録・書き手は公開ビルドから除外される（書き手が下書きなら、その人の記録も除外）。書きかけをpushしても公開されない。`npm run dev` では下書きも表示される
- 確認: ローカルで `npm run dev` で確認できる。ビルド検証は `npm run build`。下書き込みでビルドを確かめたいときは `CONTENT_INCLUDE_DRAFTS=1 npm run build`（公開ビルドでは使わない）

## 9. 技術要件

### 9.1 技術スタック

- Next.js（App Router）+ TypeScript + React
- 静的エクスポート（`output: 'export'`）。サーバー機能は使わない
- スタイル: CSS Modules + CSS custom properties（デザイントークン）
- Markdown処理: ビルド時に `content/` を読み、front-matterを解析し、HTMLに変換する（gray-matter + remark/rehype 系）
- パッケージ管理: npm
- lint は `eslint .`（Next 16 で `next lint` は廃止）。型チェックは `npm run typecheck`（`next typegen` を前置する）。`next-env.d.ts` は生成物なので追跡しない
- テストは Vitest（unified 系が ESM 前提のため）

### 9.2 静的生成

- 記録ページと書き手ページは `generateStaticParams` で全件を静的生成する
- `content/` の読み込みはビルド時のみ（サーバーコンポーネント内で `fs` を使う）。クライアントにはデータを渡した結果だけを含める
- タイムラインの「顔で絞る」はクライアント側で動作させる（データは全件をページに含める）
- 主コンテンツの一覧・フィルタ（出店情報など）は 2026年と同様、定数データをページに含めてクライアント側で絞り込む
- `trailingSlash: true` とし、GitHub Pagesのディレクトリ形式URLに合わせる
- `output: 'export'` では動的ルートの `generateStaticParams` が最低1件を返す必要がある。記録・書き手が0件のあいだはダミーの slug `_empty` を返し、そのページは not-found として出力する（sitemap には含めない）。0件でもビルドは通る

### 9.3 basePathと画像パス

- `basePath` と `assetPrefix` は `/y2027`
- Markdown本文および front-matter の画像パスは `/images/...` と書き、変換時に `basePath` を自動で付与する（rehypeプラグインまたは変換後処理）
- `next/link` と `next/image` は `basePath` を自動処理する。`next/image` は `unoptimized: true`

### 9.4 ビルド時の検証

書き手が間違えたときに、公開前に気づけるようにする。

- front-matterの必須項目、`role` と `topics` の語彙、日付形式、`kind` の値を検証し、不正ならビルドを失敗させる
- 記録の `author` が `content/people/` に存在することを検証する。無ければ、登録されているIDの一覧を添えて失敗させる
- エラーメッセージにはファイルパスと項目名を含める
- 記録slugの重複も検出する
- 参照している画像ファイルの存在確認（警告扱い。ビルドは止めない）

### 9.5 SEO・共有

- 各ページに `title`、`description`、canonical、OGPを設定する
- 記録ページのOGP画像は `thumbnail`、なければ共通画像
- JSON-LD: サイト共通に Organization + WebSite。開催日が確定したら Festival（Event）を追加する。記録ページには Article（author は書き手の名前。組織なら Organization）を付ける
- `sitemap.xml` をビルド時に生成する（主コンテンツ、記録、書き手を含む）
- `robots.txt`、`llms.txt` を用意する（2026年に準じる）
- Google Analytics（2026年と同じ測定IDを継続するか、公開前に確認）。`src/config/site.ts` の `gaMeasurementId` に測定IDを入れると有効になる

### 9.6 アクセシビリティ

- セマンティックHTML（`article`、`time`、`nav` など）
- 画像に代替テキスト。Markdownの画像記法の代替テキストを必須とはしないが、書き方ガイドで推奨する
- キーボード操作で「顔で絞る」と全リンクに到達できる。顔のボタンには名前を添え、`aria-pressed` で選択状態を示す
- 色だけに頼らない（顔には名前を併記。状態バッジは文字で示す）
- 顔の画像は装飾扱い（`alt=""`）にし、名前をテキストで出す
- コントラスト比を確保する

### 9.7 パフォーマンス

- 画像は書き手がそのまま置く前提なので、ビルド時にリサイズは行わない。代わりに、画像の推奨サイズ（長辺 1600px 以下、1枚 500KB 程度まで）を書き方ガイドに記す
- タイムラインの画像は遅延読み込み
- 外部スクリプトはGoogle FontsとGAのみ

### 9.8 テスト

- コンテンツ読み込みと検証ロジックのユニットテスト（正常系、必須項目欠落、不正な `role` や `topics`、存在しない `author`、draft の書き手の記録の除外など）
- タイムラインの並び順・月グルーピング・書き手での抽出・トピック抽出のテスト
- `npm run build` が通ることをCIで確認する

### 9.9 デプロイ

- GitHub Actions: `main` へのpushで `npm ci` → `npm run build` → `out/` を `gh-pages` に公開（2026年と同じ方式）
- 公開URL: `https://kuronekotaiwan-matsuri.github.io/y2027/`
- 公開時に、ルートリポジトリ `kuronekotaiwan-matsuri.github.io` のリダイレクト先を `/y2027/` に更新する（別リポジトリの作業）
