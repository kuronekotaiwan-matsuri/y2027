# 使用する外部サービスを README.md の「インフラ」節に書く

このプロジェクトが使う外部サービスは、ルートの `README.md` の「インフラ」節に一覧で書く。コードや設定を読み解かなくても、どのサービスに何を任せているかが分かるようにするため。

## 対象

このリポジトリの外で動いていて、アカウント、契約、設定のいずれかが必要なものを対象にする。

- ホスティングとデプロイ先
- データベース、ストレージ、キャッシュ
- 認証、決済、メール送信、通知
- アクセス解析、監視、ログ
- ドメインと DNS、CDN
- CI/CD
- 外部の API（LLM、地図、検索など）

次は対象にしない。

- ライブラリやパッケージ。依存関係の定義ファイルで分かる。
- 開発者の手元だけで使うツール。
- このリポジトリ自体を置いている Git のホスティング。ただし、その上で使っている機能（GitHub Actions、GitHub Pages など）は対象にする。

## 書く内容

「インフラ」節に、次の 3 列の表を書く。1 つのサービスを 1 行にする。

- **サービス**: サービス名。同じ事業者の別のサービスは行を分ける（例: Cloudflare Pages と Cloudflare R2）。
- **用途**: このプロジェクトで何に使っているか。
- **設定の場所**: このリポジトリで設定している場所。設定ファイルのパスや、環境変数の名前を書く。サービスを呼び出しているソースコードのパスは書かない。リポジトリの中に設定がないものは、「管理画面で設定」のように、どこで設定しているかを書く。

例:

```markdown
## インフラ

| サービス | 用途 | 設定の場所 |
|---|---|---|
| Vercel | Web アプリのホスティングとデプロイ | `vercel.json` |
| Supabase | データベースと認証 | 環境変数 `SUPABASE_URL`、`SUPABASE_ANON_KEY` |
| GitHub Actions | テストの実行 | `.github/workflows/test.yml` |
| Cloudflare | ドメインの DNS | 管理画面で設定 |
```

- 表に収まらないインフラの事情（本番と検証環境の違い、サービス間のつながり、デプロイの流れなど）は、表の下に短く書く。アプリの挙動の説明は書かない。
- 秘密の値は書かない。API キー、トークン、パスワード、接続文字列が当たる。環境変数は名前だけを書く。
- 使っているものと、使うと決まったものを載せる。検討中の候補は載せない。
- 手がかりが環境変数の名前だけのように弱いものも載せ、使っているかどうかを作業の報告でユーザーに確かめる。
- 使っているはずだが、どのサービスか特定できないもの（DNS の事業者など）は、推測で書かず、作業の報告でユーザーに尋ねる。
- 詳しい手順や構成図を別の文書に書くときも、一覧は `README.md` に置き、そこからその文書へリンクする。

## 更新するとき

次の変更をしたら、同じ作業の中で `README.md` の「インフラ」節も更新する。ユーザーから README の更新を頼まれていなくても行う。

- 外部サービスを使い始めた: 行を足す。
- 用途や設定の場所が変わった: 行を直す。
- 外部サービスを使うのをやめた: 行を消す。

## 節がないとき

- `README.md` に「インフラ」節がなければ、最初に外部サービスを載せるときに作る。そのとき、今回の変更で触れたサービスだけでなく、リポジトリから読み取れる外部サービスをすべて載せる。
- 同じ役割の節が既にあれば（「構成」「Infrastructure」など）、新しく作らずにその節に書く。
- `README.md` が日本語以外で書かれていれば、見出しと表の言語をそれに合わせる。
- `README.md` がなければ作る。
